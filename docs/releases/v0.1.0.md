# VHScribe v0.1.0

VHScribe's first stable public release provides a self-hosted workflow for operating a USB VHS
capture adapter from a browser while capture and storage remain on the Linux server.

## Highlights

- View a browser-based live preview over WebRTC through MediaMTX before and during capture.
- Start server-side recording that continues independently if the controlling browser disconnects.
- Record validated H.264/AAC MKV files with native PAL/NTSC dimensions and explicit 4:3 display
  signaling.
- Write active recordings as `.part.mkv`, rename them only after a validated stop, and recover
  interrupted partials non-destructively while preserving the source.
- Discover likely capture devices without automatically changing configuration.
- Deploy through hardened, private-by-default Docker Compose configuration.

## Known limitations

- There is no authentication or TLS; deploy only on one trusted host or trusted private LAN.
- Physical testing covers one EasierCAP-branded adapter identified as MacroSilicon MS210x, with PAL
  input on Ubuntu Server 24.04/amd64.
- NTSC and arm64 are validated through synthetic/build tests, not maintainers' physical hardware.
- One capture adapter and one active capture are supported per Compose project.
- Capture settings are fixed per service start; changing `.env` requires a recreate.
- The default H.264/AAC profile is a practical lossy capture master, not an archival lossless format.
- Automatic tape-end detection, retention policies, user accounts, and remote administration are
  intentionally absent.

## Upgrade notes

For an earlier private checkout, preserve its capture directory and create a private `.env` from
`.env.example` before recreating the stack. Existing recordings are discovered in place and are not
re-encoded. Stop an active recording before upgrade, back up `.env`, run `docker compose up -d
--build`, and then run `./scripts/verify-installation.sh`.

## Integrity and provenance

The manual container workflow can build `linux/amd64` and `linux/arm64` images with OCI metadata,
BuildKit provenance, an SBOM, and a signed GitHub build attestation. Publishing to GHCR remains a
separate, explicit manual action with `publish=true`; this source release does not claim physical
ARM64 capture validation.
